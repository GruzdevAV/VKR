## Описание

Данный модуль предназначен для генерации базы данных SQLite с аудитом с использованием средств SQLAlchemy, а также содржит некоторые вспомогательные инструменты.

Аудит осущствляется с сохранением типа данных.

Есть возможность выбрать способ аудирования: поколоночный, потабличный, погрупповой.

Для сущностей аудит проводится по каждому полю индивидуально (создаётся по таблице аудита для каждого наблюдамого поля), для отношений - целиком (таблица аудита на таблицу отношений).

Дополнительный функицонал:

- создание таблицы для хранения изображений
- создание таблицы для хранения строк
- миксин сокрытия данных

Предполагается, что:

- базой данных будет пользоваться локальное приложение (в том числе и мобильное)
- в базе данных изначально не так уж много таблиц
- вставка новых записей и обновление существующих для аудируемых таблиц будут производиться редко (может, раз в день приложение внесёт изменения в 1-10 строк 1-5 наблюдаемых таблиц, что повлечёт вставки данных в таблицы аудита)
- удаление из аудируемых таблиц будет только из таблиц отношений, но столь же редко
- чаще всего будет производиться чтение

Большое количество таблиц аудита, создаваемое данным инструментом, нужно для сохранения типизации аудированных данных и для снижения дублирования данных.

В дальнейшем планируется добавить поддержку `Room Database`.

## Функционал

### `AuditableMixin`

- Отмечает сущности и отношения для аудита
- Имеет поля:
  - `__audit_key__` - список имён полей первичных ключей
  - `__audit_observed_fields__` - список имён наблюдаемых полей (можно сгруппировать некоторые имена, то есть вставить в список не строку, а список строк, потом оно будет нормализованно)
  - `__audit_observed_groups__` - именованные списки групп имён наблюдаемых полей
  - `__audit_is_deletable__` - планируется ли удалять строки их таблицы
- можно инициировать только `__audit_observed_fields__` или только `__audit_observed_groups__`, другое будет построено само
  <!-- - `last_parsed_timestamp` - дата последнего парсинга информации -->
  - `last_changed_timestamp`

### Таблицы аудита

- создаётся по отдельной таблице аудита для каждой группы наблюдаемых полей:
  - `audit_timestamp` - дата и время вставки в таблицу аудита, часть `PK`
  - главные ключи наблюдаемой таблицы - части `PK`
  - наблюдаемые поля группы
- если `__audit_is_deletable__ = True`, создаётся таблица:
  - `audit_timestamp` - дата и время вставки в таблицу аудита, часть `PK`
  - главные ключи наблюдаемой таблицы - части `PK`
  - `is_deleted` - `False` по умолчанию, `True` в случае удаления строки из таблицы

### Триггеры аудита

- создаются 2-3 триггера:
  - `INSERT`:
    - вставляет новые данные в таблицы аудита
    - для удаляемых таблиц вставляет ключи и `is_deleted=0` в таблицу аудита существования
  - `UPDATE`:
    - вставляет изменённые данные в таблицы аудита, если произошли изменения хоть у одного поля наблюдаемой группы (как для `INSERT`, но с устловиями)
  - `DELETE`:
    - для удаляемых таблиц вставляет ключи и `is_deleted=1` в таблицу аудита существования

### Запросы к таблицам аудита

- запрос к таблицам существования
  - возвращает главные ключи с `is_deleted=0`, актуальные на момент параметра `timestamp`
- запрос к таблицам групп
  - возвращает все главные ключи и актуальные на момент параметра `timestamp` наблюдаемые поля

- Отмечает сущности и только сущности.
- `HidingMixin`:
  - `is_hiding` - отмечает, должны ли сущности, ссылающиеся на эту сущность, быть скрыты
- `HiddenMixin`:
  - `is_hidden` - отмечает, должна ли эта сущность сама быть скрытой
- Для каждой сущности, которая имеет `HiddenMixin` или связана с сущностью, которая имеет `HidingMixin`, создаются специальные `VIEW`, возвращающее только нескрытые `ID` этой сущности.

### Представления скрыток

- может быть скрыто, если
  - является `HiddenMixin`
  - имеет внешний ключ к сущности, являющейся `HidingMixin`
  - имеет главный ключ, который является внешним ключом у сущности, являющейся `HidingMixin`
  - имеет связь многие ко многим с сущностью, являющейся `HidingMixin`

### `StoredStrings` ***#TODO***

Инструмент позволяет создать таблицу `StoredStrings` для централизованного хранения строк. При создании таблицы можно выбрать параметры:

1. Хранить только строки целиком или также дельты строк.
2. Хранить только обычные строки или также сжатые строки.

Для сжатия и разжатия строк нужно использовать расширния или внешние функции.

~~Для разделения строк на дельты инструмент будет полагаться на внешнее приложение (то есть получать готовый результат для вставки в базу данных, а не делать вычисления на стороне базы данных). Важно не гнаться за наименьшим объёмом данных, а учитывть также и длину цепочки дельт.~~

Сжатие строк нужно для хранения особо больших строк. Наличие дельт нужно для хранения больших строк с небольшими изменениями.

При выборе дельт будет также создано представление для автоматического восстановления изначальных строк.

Столбцы вариантов таблицы `StoredStrings`:

1. Простая
   - `stored_string_hash_id` - `PK` SHA-256 от `stored_string_text`
   - `stored_string_text` - текст
2. С дельтами
   - `stored_string_hash_id` - `PK` SHA-256 от восстановленной строки
   - `stored_string_change` - текстовая дельта
   - `stored_string_base_id` - ID базовой строки
   - `stored_string_position` - в какое место базовой строки вставить дельту
   - `stored_string_length` - сколько символов базовой строки заменить
3. Сжатая
   - `stored_string_hash_id` - `PK` SHA-256 от разжатой строки
   - `stored_string_data` - `BLOB`
   - `stored_string_is_zipped` - сжато или нет
4. Сжатая с дельтами
   - `stored_string_hash_id` - `PK` SHA-256 от разжатой восстановленной строки
   - `stored_string_change` - `BLOB` дельта
   - `stored_string_is_zipped` - сжато или нет
   - `stored_string_base_id` - ID базовой строки
   - `stored_string_position` - в какое место базовой восстановленной строки вставить восстановленную дельту
   - `stored_string_length` - сколько символов базовой восстановленной строки заменить

Для вариантов 2-4 нужно создать `VIEW` с восстановленными строками.

**Стоит заметить, что это может быть неоптимальным способом хранения данных. Стоит пересмотреть.**

Варианты, о которых стоит подумать:

5. 3 таблицы СТРОКА-ФРАГМЕНТ:
   1. Таблица строк
      - HASH_ID SHA-256 от восстановленной строки
   2. Таблица фрагментов
      - HASH_ID SHA-256 от фрагмента строки
      - фрагмент строки
   3. Связка
      - HASH_ID восстановленной строки
      - HASH_ID фрагмента строки
      - порядок применения
6. 3 таблицы СТРОКА-ДЕЛЬТА:
   1. Таблица строк
      - HASH_ID SHA-256 от восстановленной строки
   2. Таблица дельт
      - HASH_ID SHA-256 от фрагмента строки
      - фрагмент строки
   3. Связка
      - HASH_ID восстановленной строки
      - HASH_ID фрагмента строки
      - порядок применения
      - позиция применения
      - сколько символов заменить
